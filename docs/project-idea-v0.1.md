# 개인용 시각적 문서 워크스페이스

아이디어 설명서 v0.3 | 검토용 초안

## 1. 한 문장으로 설명하면

**AI가 프로젝트 맥락을 바탕으로 기획서와 설계서를 생성하고 보완을 제안하며, 작성자가 시각적으로 이해하고 수락·거절하며 발전시키는 로컬 작업 공간.**

아이디어만 있는 상태와 기존 문서가 있는 상태 모두에서 시작할 수 있다. 문서를 만들고, 연결하고, 이해하고, 수정하는 과정이 같은 작업 공간에서 이어진다.

## 2. 이 아이디어가 출발한 문제

AI와 대화하면 명세서, 기획서, 설계서가 빠르게 만들어진다. 하지만 결과가 긴 Markdown 문서나 채팅 답변에 모이면서 다음 문제가 생긴다.

- 제목과 문단은 있지만 전체 구조가 한눈에 들어오지 않는다.
- 요구사항이 어떤 기능, 화면, 설계와 이어지는지 머릿속으로 연결해야 한다.
- 문서가 늘어나면 같은 내용이 어디에 있는지 찾기 어렵다.
- 한 부분을 수정했을 때 함께 검토해야 할 문서가 무엇인지 알기 어렵다.
- AI에게 질문할 때마다 어떤 문서의 어느 부분인지 다시 설명하게 된다.
- AI가 이전 결정이나 제외한 범위를 놓쳐, 서로 모순되는 문서와 제안을 만들기도 한다.
- AI의 제안과 작성자가 확정한 내용이 섞여 무엇이 실제 결정인지 불분명해진다.

이 프로젝트의 목적은 **프로젝트 맥락을 유지하면서 필요한 문서를 함께 만들고, 내용을 시각적으로 이해하며, 작성자가 변경을 판단할 수 있게 하는 것**이다. 새 문서 생성, 기존 문서 보완, 시각적 탐색은 모두 핵심 기능이다.

## 3. 사용자와 사용 환경

첫 사용자는 Codex와 Gemini를 활용해 개인 프로젝트를 기획하고 개발하는 사람이다. 우선 본인이 쓰기 편한 도구로 만든다는 가정이다.

macOS와 Windows에서 설치해서 사용하는 데스크톱 프로그램으로 만든다. 기본적인 문서 작성·편집·탐색·저장은 별도 서버나 인터넷 연결 없이 동작하고, 클라우드 AI 기능은 네트워크 연결이 필요하다.

프로젝트와 문서는 로컬에 보관한다. AI를 사용하는 순간에는 선택한 내용이 해당 서비스로 전송될 수 있으므로, 로컬 저장과 오프라인 AI 실행은 구분한다.

현재 사용하는 Codex와 Gemini를 연결 대상으로 고려하되, 구독을 활용할 수 있는 구체적인 연결 방식은 별도로 확인한다. 이 초안은 연결 가능성이나 추가 비용 없음을 확정하지 않는다.

### GitHub 공개와 배포

소스 코드를 GitHub에 공개하고 다른 사람도 설치해 사용할 수 있는 프로젝트를 목표로 한다. 공개 시 사용할 라이선스는 별도로 결정한다.

- README에 목적, 실행·설치 방법, 지원 OS, AI 연결 조건을 명시한다.
- 실제 개인 문서와 인증정보를 포함하지 않는 예제 프로젝트를 제공한다.
- macOS와 Windows의 빌드·기본 검증을 자동화하고, GitHub Releases에 OS별 설치 파일을 배포한다.
- 설치 파일 서명과 macOS 공증에 필요한 계정·인증서·비용은 배포 설계에서 확인한다.
- AI 로그인 정보와 개인 프로젝트 데이터는 공개 저장소 및 배포 파일에서 제외한다.

데스크톱 프레임워크는 Tauri와 Electron을 후보로 검토한다. 선택 전 Codex·Gemini 연결, 파일 접근, 다이어그램 표시를 양쪽 OS에서 검증한다. 설치형 앱이라는 목표와 실제 AI 구독 연결 가능성은 별도로 검증한다.

## 4. 사용자가 경험할 핵심 흐름

1. **시작하기:** 아이디어를 대화로 설명하거나 기존 Markdown 문서를 가져온다.
2. **맥락 정리하기:** AI가 목표, 범위, 제약, 기존 결정을 정리하고 불확실한 내용은 질문한다.
3. **초안 만들기:** AI가 필요한 새 문서와 기존 문서의 보완안을 제안한다.
4. **전체 흐름 보기:** 제목별로 나뉜 내용과 문서 지도, 다이어그램으로 구조와 연결을 확인한다.
5. **함께 발전시키기:** 작성자가 질문하거나 맥락 검토를 실행하면 AI가 누락, 모순, 추가사항과 영향받는 문서를 제안한다.
6. **수락·거절하기:** 작성자가 제안별 근거와 변경 내용을 확인해 수락하거나 거절하고, 필요하면 수정 요청을 한다.
7. **연결 검토하기:** 수락한 변경에 따라 함께 수정해야 할 문서와 다이어그램을 검토한다.
8. **개발에 활용하기:** 확정한 내용을 Markdown으로 내보내거나 프로젝트 폴더에서 활용한다.

## 5. 문서를 나누는 방식

Markdown의 제목을 구조화의 출발점으로 사용한다. 다만 모든 제목을 별도 파일로 만드는 것은 피한다.

- `#`: 문서의 이름 또는 가장 큰 주제
- `##`: 화면에서 독립적으로 탐색할 수 있는 주요 섹션
- `###` 이하: 해당 섹션 안의 하위 내용이며, 필요할 때 별도 항목으로 분리

예를 들어 하나의 PRD 안에 있는 '목표', '사용자', '핵심 기능'을 각각 선택해서 읽을 수 있다. 기능이 커지면 별도의 기능 명세로 분리하고 원래 PRD에서 연결한다.

**문서, 문서 안의 섹션, 문서 사이의 연결을 구분한다.** 화면에서 나누어 보더라도 원래 제목 계층과 본문의 순서를 유지하고, 전체 문서로도 읽을 수 있어야 한다.

## 6. 기본 문서 유형

대화에서 언급한 Manyfast를 참고 대상으로 이해했다. 기획부터 개발로 이어지는 문서 구성을 참고하되, 개인 프로젝트에 필요한 유형만 꺼내 쓰는 방향이다.

| 문서 유형 | 담는 내용 | 주요 연결 대상 |
| --- | --- | --- |
| 아이디어·개요 | 만들려는 것, 해결할 문제, 대상 사용자 | PRD |
| PRD·요구사항 | 목표, 범위, 요구사항, 완료 기준 | 기능 명세, 사용자 흐름 |
| 기능 명세 | 기능별 동작, 조건, 예외 | 화면, 데이터, 관련 요구사항 |
| 사용자 흐름 | 사용자의 단계와 선택, 성공·실패 경로 | 기능, 화면 |
| 화면 정의·와이어프레임 | 화면의 구성과 상태, 이동 경로 | 기능, 사용자 흐름 |
| 기술 설계 | 구성 요소, 데이터 흐름, 인터페이스 | 기능, 데이터 구조 |
| 결정 기록·미해결 질문 | 선택 이유, 대안, 아직 결정하지 않은 점 | 관련 문서 또는 섹션 |

모든 프로젝트에 이 문서들을 강제하지 않는다. 짧은 프로젝트는 개요와 기능 명세만으로 시작할 수 있고, 일반 문서 유형도 허용한다.

## 7. 눈으로 이해하는 세 가지 보기

### 문서 지도

프로젝트의 문서와 주요 연결을 보여준다. 처음에는 주요 문서 수준으로 보여주고, 선택한 부분의 세부 연결을 펼친다. 연결이 많아져도 전체 화면이 복잡한 선으로 가득 차지 않게 한다.

연결에는 '이 요구사항을 구현함', '이 화면에서 사용함', '이 결정의 근거임'처럼 의미를 붙인다. AI가 추정한 연결과 사용자가 확인한 연결을 구분한다.

### 구조화된 문서 보기

왼쪽에는 제목 계층과 문서 목록, 가운데에는 선택한 섹션, 주변에는 관련 문서와 질문을 배치한다. 부분에 집중하면서도 현재 위치와 상위 문서를 잃지 않는 것이 중요하다.

### 내용에 맞는 다이어그램

사용자 동작은 흐름도, 시스템 구성은 구성도, 호출 순서는 시퀀스 다이어그램처럼 표현한다. 문서 간 연결 지도와 문서 내용의 다이어그램은 서로 다른 보기다.

처음에는 사용자 흐름도와 시스템 구성도에 집중한다. AI가 원문에 없는 구조를 제안하면 추정임을 표시하고, 원문에 근거한 요소는 해당 섹션으로 이동할 수 있게 한다.

## 8. AI와 대화하는 방식

### 프로젝트 맥락이 기준

대화는 프로젝트 전체를 대상으로 시작하거나 특정 문서·섹션에 집중할 수 있다. 일부를 선택하더라도 프로젝트 목표, 제약, 확정된 결정과 관련 문서의 맥락을 함께 고려한다.

맥락에는 다음 내용을 포함한다.

- 프로젝트의 목적, 대상 사용자, 포함·제외 범위와 제약
- 현재 문서와 연결된 요구사항, 기능, 화면, 설계
- 작성자가 수락한 결정과 그 근거
- 거절한 제안과 거절 이유가 있는 경우 그 이유
- 미해결 질문과 아직 확인되지 않은 AI의 가정

문서와 수락된 변경을 맥락의 기준으로 삼고, 대화에서 나온 미확정 아이디어는 구분한다. AI에 전달할 관련 내용을 선택해 보여주며 작성자가 추가하거나 제외할 수 있게 한다. 필요한 근거가 없거나 문서끼리 충돌하면 확정 사실로 취급하지 않고 질문하거나 충돌을 알린다.

새 문서를 만들 때도 기존 문서와 결정을 참고한다. 예를 들어 PRD에서 '회원가입 없이 사용'으로 확정했다면, 새 화면 정의서에 회원가입 화면을 임의로 추가하지 않는다. AI가 회원가입의 필요성을 발견했다면 기존 결정의 변경 제안으로 제시한다.

### 생성과 보완을 이어가는 대화

예시 요청:

- '이 아이디어로 PRD와 첫 기능 명세를 만들어줘.'
- '기존 PRD를 보고 아직 없는 화면 정의서를 작성해줘.'
- '문서 전체에서 빠진 예외 처리나 서로 모순되는 내용을 제안해줘.'
- '이 기능을 사용자가 누르는 순서로 보여줘.'
- '실패했을 때 흐름도 추가해줘.'
- '이 설계가 어떤 요구사항 때문에 필요한지 연결해줘.'
- '로그인을 없애면 함께 검토해야 할 부분을 찾아줘.'
- '이 부분을 쉬운 말로 설명하고 구성도로 보여줘.'

AI는 설명뿐 아니라 새 문서 초안, 추가사항, 본문 수정안, 연결 제안, 다이어그램 초안을 제시한다. 문서 생성·수정 후 또는 작성자가 맥락 검토를 실행할 때 관련 보완사항을 제안하며, 구체적인 자동 검토 시점은 상세 설계에서 정한다.

### 작성자가 수락하거나 거절하는 제안

제안에는 대상 문서·섹션, 제안 이유, 근거가 된 문서나 결정, 추가·변경될 내용, 관련 문서에 미치는 영향을 보여준다. 새 문서는 초안 전체를, 기존 문서 수정은 변경 전후를 확인할 수 있게 한다.

작성자는 각 제안을 **수락**, **거절**, **수정 요청**할 수 있다. 검토 대기 중이거나 거절한 내용은 확정 문서에 반영하지 않는다. 수락하면 해당 내용을 저장하고 문서 연결과 다이어그램에 미치는 영향을 다시 확인한다. 다른 문서의 의미까지 바뀌는 경우에는 추가 제안으로 검토한다.

한 제안이 다른 변경을 전제로 하면 그 의존 관계를 표시한다. 제안 생성 이후 대상 문서가 수정되었다면 최신 내용과 다시 비교한 뒤 수락할 수 있게 한다. 제안의 처리 이력을 남기고, 거절된 제안을 같은 근거로 반복하지 않도록 한다. 거절 이유 입력은 선택 사항이다.

## 9. 개인적인 느낌과 화면 방향

프로젝트를 열면 문서 목록만 나오는 대신 **프로젝트 개요, 주요 문서의 관계, 검토 대기 제안, 미해결 질문**을 함께 볼 수 있게 한다. 새 프로젝트에서는 아이디어 입력과 새 문서 작성으로 바로 시작할 수 있게 한다.

화려한 대시보드보다 읽고 생각하기 편한 작업 공간을 지향한다. 문서 유형은 절제된 색과 아이콘으로 구분하고, 제목과 본문에 충분한 공간을 준다. 그래프 보기와 목록 보기를 선택할 수 있어야 한다.

개인적인 느낌은 장식보다 작업 방식에서 만든다. 문서 이름과 구성을 바꾸고, 자주 보는 문서를 고정하고, 자신의 메모와 결정 이유를 남길 수 있게 한다. 팀 승인 절차나 복잡한 역할 관리는 초기 범위에서 제외한다.

## 10. 첫 버전의 제안 범위

**먼저 검증할 질문: 아이디어 또는 기존 문서에서 시작해, AI가 맥락에 맞는 문서와 보완안을 제안하고 작성자가 시각적으로 이해하며 수락·거절할 수 있는가?**

첫 버전에는 다음 기능을 제안한다.

- 로컬 프로젝트 생성과 Markdown 가져오기·저장·내보내기
- 아이디어 대화와 기존 문맥을 바탕으로 한 새 문서 생성
- 제목 계층에 따른 섹션 탐색과 전체 문서 보기
- 문서·섹션 사이의 수동 연결과 관련 문서 이동
- 주요 문서의 관계를 보여주는 문서 지도
- 프로젝트 목표·제약·결정과 관련 문서를 고려하는 AI 대화
- 누락·모순·추가사항 제안과 근거·변경 전후 확인
- 제안별 수락·거절·수정 요청과 처리 이력
- 사용자 흐름도 또는 시스템 구성도 생성과 원문 연결

AI 연결은 실제 지원 방식을 확인한 뒤 하나부터 붙인다. 문서 분할과 탐색은 먼저 검토할 수 있지만, 첫 버전의 완료 기준에는 실제 AI를 통한 문서 생성과 제안 검토 흐름도 포함한다.

팀 협업, 클라우드 동기화, PDF·Word 가져오기, 자유로운 와이어프레임 편집, 여러 AI의 자동 협업은 이후 검토 대상으로 둔다.

## 11. 성공 여부를 판단하는 기준

- 문서가 없는 상태에서 아이디어를 대화로 설명하고 새 문서 초안을 만들 수 있다.
- 기존 문서의 목표·제약·결정을 반영해 추가 문서를 생성할 수 있다.
- 실제 기획서 한 개를 가져와 목표, 핵심 기능, 사용자 흐름의 위치를 쉽게 찾는다.
- 기능에서 관련 요구사항과 설계로 이동하고 다시 돌아올 수 있다.
- 다이어그램의 요소가 어떤 원문에 근거하는지 확인할 수 있다.
- 특정 부분에 대한 질문을 문맥을 다시 복사하지 않고 이어갈 수 있다.
- 수정 전후를 확인하고 원하는 변경만 반영할 수 있다.
- 제안의 근거와 영향을 확인하고 수락·거절·수정 요청할 수 있다.
- 거절한 내용은 확정 문서에 반영되지 않고 이후 맥락에서도 거절 사실을 유지한다.
- 수락한 변경은 이후 생성·검토의 맥락에 반영되고, 충돌하는 관련 문서를 확인할 수 있다.
- 앱에서 구조화한 내용을 Markdown으로 다시 내보내도 제목 계층과 본문이 유지된다.

## 12. 검토할 핵심 방향

이 초안은 **본인이 사용하는 개인용 도구**, **프로젝트 맥락을 바탕으로 한 새 문서 생성과 기존 문서 보완**, **시각적 이해**, **작성자의 제안 수락·거절**을 중심으로 작성했다. 새 문서 생성은 첫 버전부터 포함하는 핵심 기능이다.

컨펌 시에는 이 중심 방향과 첫 버전의 범위가 의도에 맞는지 확인한다. 제품명, 세부 화면 배치, 기술 스택은 아직 결정하지 않았다.
