# 아이디어에서 시작하는 소프트웨어 프로젝트 설계

## 목적

문서가 없는 프로젝트에서도 사용자가 AI와 대화하며 아이디어를 발전시키거나 바로 계획을 세울 수 있어야 한다. 사용자의 설명과 결정이 프로젝트 개요·요구사항·사용자 시나리오·개발 계획으로 이어지고, 생성된 문서를 기존 문서 구조 및 유저플로우 기능에서 사용할 수 있어야 한다.

사용자 요청은 빈 프로젝트의 브레인스토밍/플랜 시작과 소프트웨어공학적인 진행이다. 소프트웨어 제품·서비스 기획을 첫 적용 대상으로 가정한다. 문서 양식을 채우기 전에 사용 목적·대상 사용자·범위를 구체화한다.

## 현재 문제

- 빈 프로젝트의 브리핑이 문서·연결·흐름 0개를 보여주며 기존 문서 탐색을 권한다.
- 새 기획서 작성과 AI와 시작은 입력 문장만 채운다. 문서 모드에서는 근거가 없어 제공자 호출 전에 막힌다.
- 아이디어 상담은 사용자가 별도 체크박스로 선택해야 한다.
- 대화는 화면에 남지만 AI 요청에는 현재 instruction과 문서/결정 등이 전달된다. Codex는 요청마다 새 thread, Claude는 단일 user payload를 사용한다. 이전 대화를 명시적으로 다음 요청에 포함하는 계약이 필요하다.

## 시작 경로

등록 문서가 0개이거나 기존 근거 검사에서 실제 본문이 없는 빈 문서만 있는 프로젝트는 시작 상태로 취급한다. 기본 브리핑은 다음 두 작업을 중심으로 표시한다. 가져오기/직접 작성은 보조 경로로 유지한다.

1. **브레인스토밍 시작:** 막연한 아이디어에서 문제·사용자·대안·차별점·가정을 함께 정리한다.
2. **바로 계획 세우기:** 이미 정한 아이디어와 제약을 받아 MVP 범위·요구사항·핵심 시나리오·개발 순서를 정리한다. 빠진 정보만 질문한다.

기존 새 기획서 작성 진입점도 빈 프로젝트에서는 계획 세우기로 연결한다. 기존 문서 검토/문서 기반 유저플로우 생성의 근거 검증은 유지한다. 문서가 있는 프로젝트에서도 사용자가 명시적으로 새 아이디어 작업을 시작할 수 있다.

## 소프트웨어공학적 진행

단계는 되돌아가 수정할 수 있으며 고정된 질문 수나 모든 문서의 일괄 생성을 강제하지 않는다. 브레인스토밍과 계획 세우기는 출발 지점이 다르고 같은 기획 상태를 공유한다.

| 단계 | 정리할 내용 | 검토할 산출물 |
|---|---|---|
| 문제 정의 | 해결할 문제, 대상 사용자, 목표, 현재 대안 | 프로젝트 개요 |
| 범위 정의 | MVP, 제외 범위, 제약, 성공 기준 | 범위와 핵심 요구사항 |
| 요구사항 분석 | 사용자 역할, 기능/비기능 요구사항, 우선순위, 확인할 가정 | 요구사항 문서 |
| 사용자 시나리오 | 주요 사용 사례, 정상/실패/예외 경로 | 사용자 시나리오 문서 |
| 구현 계획 | 작업 순서, 의존성, 완료 기준, 검증 방법 | 개발 계획 |

아키텍처·데이터 모델·API 설계는 요구사항에 따라 후속 단계로 제안한다. 첫 문서화에서는 프로젝트 개요·MVP 요구사항·핵심 사용자 시나리오를 기본 후보로 제시하고 사용자가 조정한다. 개발 계획은 범위 확인 후 구체화한다.

## 대화와 진행 상태

- 프로젝트에 귀속되는 기획 세션에 시작 경로, 현재 단계, 대화, 확인된 결정, 열린 질문, 가정, 문서화 상태를 보존한다.
- 다음 AI 요청에 사용자가 검토할 수 있는 이전 대화와 현재 기획 상태를 포함한다. 예산을 넘기면 조용히 누락하지 않고 포함 범위와 빠진 내용을 표시한다.
- 중단/재시작/프로젝트 전환 후 같은 기획을 이어간다. 서로 다른 프로젝트의 대화는 섞지 않는다.
- AI는 현재 단계에 필요한 질문부터 하고 기존 답변을 재사용한다. 사용자의 요청으로 단계 이동, 이전 결정 수정, 바로 초안 작성이 가능해야 한다.
- 확인된 내용과 AI 제안/가정을 구분한다. 진행 상태의 AI 보완도 사용자 검토 대상이며 미수락 제안을 확정된 사실로 취급하지 않는다.

## 문서화와 기존 기능 연결

1. 사용자 입력과 검토한 기획 상태에서 문서 초안을 제안한다. 기존 문서가 없어도 시작 가능하다.
2. 각 문서의 목적·주요 내용·미확정 가정을 검토하고 수정/제외/수락한다. 단순 상담만 원하면 문서 생성을 강제하지 않는다.
3. 수락한 초안만 기존 문서 저장 경로로 생성한다. 기존 문서 덮어쓰기는 별도 revision 검토를 거친다.
4. 저장한 요구사항·시나리오 문서에서 근거를 검토해 구조화된 유저플로우를 제안한다. 근거 없는 유저플로우 전송을 허용하도록 기존 검증을 완화하지 않는다.
5. 문서 관계는 제안으로 검토한다. 현재 proposal의 의존 변경 제한을 유지하며 문서 생성 후 관계/플로우를 후속 요청한다.

## 화면 방향

- 빈 브리핑의 0개 통계 카드 대신 시작 경로와 짧은 설명을 보여준다.
- 본문에는 현재 단계와 기획 정리 내용을, 어시스턴트에는 대화와 질문을 표시한다. 전체 대화와 기획 상태에 접근할 수 있어야 한다.
- 기획 상태는 완료/실패를 과장하는 진행률 대신 현재 단계·확정 내용·남은 질문으로 표시한다.
- 문서가 생기면 기존 브리핑/문서 구조/사용자 흐름을 사용하며 기획 세션으로 돌아갈 수 있다.

## 완료 기준

- 문서 0개 및 본문이 없는 빈 문서만 있는 프로젝트에서 두 시작 버튼으로 실제 AI 대화 경로에 진입하고 원문 근거 없음 모달에 막히지 않는다.
- 빈 프로젝트의 새 기획서 작성도 계획 세우기로 연결한다.
- 사용자가 이전 턴에서 답한 대상 사용자·목표·제약이 다음 요청에 포함된다. 재시작 후에도 보존된다.
- 단계 확인/되돌아가기와 사용자 결정 수정이 가능하며 프로젝트 전환 시 기획 상태가 격리된다.
- 사용자 입력에서 문서 초안을 생성할 수 있고 수락 전에는 문서가 생성되거나 덮어써지지 않는다.
- 수락한 문서로 기존 근거 검토·문서 구조·유저플로우 생성 경로를 사용할 수 있다.
- 원문 기반 검토의 근거/예산/revision 검증, 제공자의 도구 금지, 문서의 비신뢰 입력 처리를 유지한다.
- 실제 AI 호출 없이 가짜 제공자로 빈 프로젝트 시작, 다중 턴 payload, 저장/복원, 문서 수락 및 기존 문서 모드 회귀를 검증한다.

## 범위와 미결정 사항

첫 구현은 아이디어 정리부터 첫 문서·개발 계획까지다. 코드 생성/실행, 외부 조사, 자동 기술 스택 결정, 자동 배포는 포함하지 않는다. 기존 프로젝트와 저장 데이터는 보존한다.

구현 계획에서 세션 저장 계약과 기존 이력의 호환 방식, 요청 예산 내 대화 선택 규칙, 단계 확인 UI를 구체화한다. 구현 착수 전 이 설계 문서를 사용자와 검토한다.
